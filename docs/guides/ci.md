# CI gates

What Docent's CI enforces on a pull request, on a push to `main` and on a schedule, workflow by workflow. For each gate: its trigger, what it verifies, and what turns it red. Also the time bounds and caches the jobs carry, the action SHA-pinning policy, and the workflow-security posture behind the whole set. This guide covers **what** the gates are. Its companion, [Running CI locally](local-ci.md), covers **how** to run them on your own machine (per-gate direct commands, whole jobs under `act`, and the Windows-runner boundary), and is not repeated here. The workflow files under [`.github/workflows/`](../../.github/workflows/) decide throughout: where this prose and a workflow disagree, the workflow governs.

Each rule this document makes in its own right carries a stable identifier
(**CI-n**) so other documents, reviews,
and checks can cite it precisely. Identifiers are never renumbered; a retired
identifier stays reserved and is never reused. How each rule is verified — by an
existing named check, by a check that could be built, or by judgment — is
recorded per rule in the [clause registry](../clause-registry.json). The key
words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). Keywords appear on a
clause's operative requirement where it has one; definitional clauses bind as
stated without a keyword, and subsidiary absolutes inside a clause inherit its
force. A clause's scope runs from its marker to the next marker or heading;
identifiers reflect minting order and can appear out of numeric sequence.

Two entries live outside the table's closure:

- **CodeQL** runs with no workflow file. It is GitHub's default-setup code scanning, enabled in the repository settings rather than in the tree. Its alerts land under the repository's Security → Code scanning view (the README badge links there). Its findings have driven in-repo changes such as the least-privilege `permissions:` blocks in the publish workflows.
- **Dependabot** ([`dependabot.yml`](../../.github/dependabot.yml)) is configuration, not a workflow. It opens weekly dependency-update PRs for:
  - every npm root the [dependency audit](#dependency-and-license-audit) reads;
  - the desktop cargo crate and the Win32 bindings generator's crate. The Win32 bindings freshness gate holds the two crates' `windows-core` and `windows-bindgen` pins on one `0.<minor>` version line, and the committed bindings equal to a fresh run. So a bot PR that moves either pin off the shared line, or changes the generator's output, stays red. A minor-line bump lands as one change that moves both pins and regenerates the bindings. A `windows-bindgen` bump whose output differs needs the regeneration pushed onto the bot's branch. A bump that changes neither passes as it is;
  - the `github-actions` ecosystem (its pinning role is [below](#every-action-is-pinned-to-a-commit-sha)).

  Each entry except the bindings generator's (its only dependency is the `windows-bindgen` pin) groups its minor and patch version updates into one PR. Security updates are not grouped, so each advisory opens its own PR when its fix is published. A major version update also arrives on its own PR. Dependabot reads a `0.x` version as major.minor.patch, so a `0.x` line change joins its group as a minor update. The `windows-core` pin is excluded from its group, so a line bump of either pin keeps a PR of its own. The shared unit suite holds its npm entries to the audited roots.

The three release workflows (`publish.yml`, `publish-desktop.yml`, `next-release-version.yml`) are named here only for closure. [PUBLISHING](../../.github/PUBLISHING.md) governs their modes (final / pre-release / dry-run), gating, version PR and secrets, and this guide does not restate them. One CI-relevant fact: each publish workflow **calls `test.yml` as a reusable workflow** for the release commit, so a release can never publish with red tests. A `platform` input scopes the call to that platform's jobs plus the shared ones (see [PUBLISHING § Test gating](../../.github/PUBLISHING.md#test-gating-and-the-version-pr)).

## The PR checks outside the test suite

### Docs disposition format

[`docs-disposition.yml`](../../.github/workflows/docs-disposition.yml) runs [`check-docs-disposition.js`](../../scripts/check-docs-disposition.js) on every PR open/edit/reopen/synchronize. Editing the PR body re-runs it. The check derives:

- from [`area-map.json`](../../scripts/area-map.json), the set of docs governing the changed code, together with each governing doc the change itself edits (which owes its own line alone);
- the `judgment-only` clause list, from [`clause-registry.json`](../clause-registry.json).

It then verifies two sections:

- `## Docs disposition` carries exactly one `updated:`/`unaffected:` line per governing doc. A `judgment-only` clause of such a doc may take a line of its own; none is owed.
- `## Change record` carries its structural markers.

It checks **form only**: reviewers read the reasons, and CI never judges them. Its red output lists the exact lines it expects.

Where the check cannot use a governance-data file, it refuses with that file's own verdict, in place of expected lines derived from a scope it cannot resolve:

| The check cannot use                                                                 | It prints                                                       | It ends on                                                                                              |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| [`area-map.json`](../../scripts/area-map.json): it read, but its shape failed        | The map's own verdict: the shape errors, enumerated as found    | The ordinary red path a body missing its lines takes                                                    |
| `area-map.json`: its text is not JSON, or the file could not be read at all          | The map's own verdict: the one reason, in place of shape errors | The same red path                                                                                       |
| [`clause-registry.json`](../clause-registry.json): it cannot be read as the registry | The single-sentence verdict that file's own check states        | The check's own exit code, which every command line loading the registry through the shared home shares |

The two files end on different codes deliberately.

Some diffs are admitted without the sections, each class by a stated test over stated inputs:

- The dependency-only class is decided from the diff alone.
- The release pipeline's own regeneration PR is decided from the diff together with a head branch. That branch is derived from the pull request's own head branch and head repository. Under a GitHub Actions run, it is a branch this repository carries and no other. With no Actions context around it, it is the head ref as supplied.

A diff whose changed files are the area map, alone or with the clause registry, records one `governance-data-only:` line in place of the per-doc lines. A registry-only diff is outside that class. The map declares the registry governed by no doc, so its governing doc set is empty and the section stays with no lines and no marker. The marker set, the admitted classes with their admission tests, and how to write the sections: [CONTRIBUTING § Docs Disposition and Change Record](../../.github/CONTRIBUTING.md#docs-disposition-and-change-record).

#### How the check reads a body

The check reads each section the way CommonMark parses the body:

| In the body                                                                                                    | The check reads                                                                                      |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A line in a Markdown code block: copied with its fence around it, or indented four spaces where a block starts | An example, which records nothing                                                                    |
| A line inside a `<details>` block written without a blank line after its opener, or inside a `<pre>` element   | A line of the section, since those are HTML the body carries rather than code blocks                 |
| Everything from an `<!--` to its `-->`, even when the opener is shown inside an example                        | Nothing, which is why the template's own notes are inert                                             |
| An unclosed fence                                                                                              | Code to the end of whatever holds it: at a body's top level, the rest of the body, headings included |
| An unclosed comment                                                                                            | Nothing in the rest of the body, so the sections below it are no longer sections the check can find  |
| Any other line the section shows                                                                               | A line of the section                                                                                |

### PR title

[`pr-title.yml`](../../.github/workflows/pr-title.yml) runs [`check-pr-title.js`](../../scripts/check-pr-title.js) on the same PR events. The title must parse as a Conventional Commit (`type(optional-scope)!?: summary`, with the recognized type list in the script). Docent squash-merges, so the PR title becomes the commit subject on `main` and feeds release versioning (see [CONTRIBUTING § Pull Request Guidelines](../../.github/CONTRIBUTING.md#pull-request-guidelines)).

### CLA assistant

[`cla.yml`](../../.github/workflows/cla.yml) prompts on each PR and records signatures on a dedicated `signatures` branch. The check stays red until the author posts the exact signing comment the bot requests. Bots (Dependabot) are allowlisted. It is the repository's one `pull_request_target` workflow. A plain `pull_request` trigger cannot replace that trigger here, because fork PRs need the write-capable token to receive the bot's comment (the mitigations are [below](#workflow-permissions-and-credentials)).

## The test suite (`test.yml`)

[`test.yml`](../../.github/workflows/test.yml) runs on every PR to `main`,
every push to `main`, and as the reusable gate inside a publish.

### The `changes` paths filter

The first job, `changes`, computes which parts of the tree the diff touches
(via `dorny/paths-filter`) and exposes one flag per part. The subtree-scoped
flags name the tree they watch: `extension` (`packages/extension/**`),
`desktop` (`packages/desktop/**`), `shared` (`packages/shared/**`), `schema`
(`schemas/**`), `referenceServer` (`reference-implementations/**`), and
`corpus` (`corpus/**`). The rest carve up the CI machinery so a change fires
only the jobs that can observe it:

- `ciCore` — inputs every job's build/run depends on: this workflow
  (`test.yml`), the composite actions under `.github/actions/**`, and the root
  npm manifests (`package.json`, `package-lock.json`). Sets every test job.
- `buildScripts` — the scripts a non-`unit-tests` job actually executes, plus their `scripts/`-local import/spawn closure (`sync-shared`, `build-schemas`, `build-validators`, `inject-shared-views`, `build-desktop-dist`, `corpus-compare`, `sufficiency-lint`, and the corpus/vector assemblers). Sets the heavy test jobs, but not `desktop-cross-compile`, which runs none of them.
- `ci` — the broad `scripts/**` bucket (plus `.c8rc.json`), gating `unit-tests`
  only: its shared unit suite exercises most scripts through
  `packages/shared/tests/unit/check-*.test.js`.
- `releasePipeline` — the publish workflows and the release-output guard script. It gates each job whose suite holds those committed files: `reference-server-tests`, through its release-exclusion suite, and `unit-tests`, through its disposition suite. The CI path-filter check's [`HELD_FLAG_HOLDINGS`](../../scripts/check-ci-filter.js) map states beside each entry what holds it, in which job. That map is the home of the holdings of this flag, `contractDocs` and `dispositionWorkflow`, and the same check holds it to the filter both ways.
- `contractDocs` — the contributor contract files (`CONTRIBUTING.md` and the PR template), gating `unit-tests` alone. Its disposition suite reads them as files and welds itself to a surface in each. The same `HELD_FLAG_HOLDINGS` map states the surfaces beside each entry.
- `dispositionWorkflow` — the docs-disposition workflow, gating `unit-tests` alone. Its release-output suite reads that workflow's guard step as a file. The same `HELD_FLAG_HOLDINGS` map states the holding beside the entry.
- `suiteHeld` — the files a `unit-tests` suite or step holds, asserting over their content in a way no always-on gate holds. Without the flag, a docs-only edit to one would red `main` alone on the push run. It gates `unit-tests` alone. The clause-carrying documents the clause registry names join as a class: the preamble suite holds each one's registry link as raw text, and the CI path-filter check holds the list to the registry. That check's [`SUITE_HELD_HOLDINGS`](../../scripts/check-ci-filter.js) map states beside each entry what holds it: the suite or step asserting over its content. The map is the home of those holdings, and the same check holds it to the filter both ways. Every entry is a literal path the check holds to a tracked file.

The narrow flags above are narrow on purpose. Each names files only `unit-tests`' suites hold, so an edit reaches the job holding them and no heavy job beyond it.

A file outside the package trees (this workflow and its composite actions, a sibling workflow, a contributor contract file, the root npm manifests, a root config, a script, a schema, a corpus file, a document, the clause registry, a reference implementation, the Codecov configuration) sets a flag for one of two reasons:

1. **Some path-filtered job's run depends on it.**
   - This workflow, the composite actions and the root npm manifests set `ciCore` for every job.
   - The scripts a heavy job executes set `buildScripts`.
   - Every script and the coverage config `.c8rc.json` set `ci` for `unit-tests`.
   - The schemas and the corpus set `schema` and `corpus` for the jobs that read them.
   - The reference implementations set `referenceServer` for the end-to-end, desktop-integration and reference-server jobs, whose runs execute the reference server. They set it for the control-client job, whose run executes the reference control client, and for the mcp-server job, whose run executes the reference MCP server on that client.
2. **A test suite holds it.**
   - The reference implementations again, through that same flag, for `unit-tests` (a shared suite walks them for resolution-procedure tokens).
   - The publish workflows and the release-output guard, through `releasePipeline`, which reaches `reference-server-tests` and `unit-tests`.
   - `CONTRIBUTING.md` and the PR template, the docs-disposition workflow, and the files `suiteHeld` names, each through its own narrow flag, reaching `unit-tests` alone.

A file outside the package trees that a suite reads only while re-running one of the always-on `lint` job's gates over the committed tree, or only as one of every tracked source under a lock on the suite's own machinery, sets no flag, because that gate reds the same drift on every PR and that lock asserts nothing about the file: `cla.yml` and `pr-title.yml` among the sibling workflows (the workflow-bounds suite re-runs its check over them), and `.github/codecov.yml`, the Codecov configuration (the clause-governance suite's citation walk). A file no suite reads and no path-filtered job's run depends on sets none either: `.editorconfig` and `.prettierrc` among the root configs. `eslint.config.js` is read both ways. The clause-governance suite's citation walk and the test-inventory suite's every-tracked-source lock (which asserts that suite's own tokenizer) read it without asserting its content. The lint-glob guard's reach case asserts its ignore patterns, so the file sets the `suiteHeld` flag. The always-on `lint`, `zizmor`, `actionlint`, `dependency-audit`, and `coverage-upload` jobs are what cover both.

The split is a committed contract: [`check-ci-filter.js`](../../scripts/check-ci-filter.js) (`npm run lint:ci-filter`, in the `lint` job) recomputes the `buildScripts` closure and the gate invariants and reds on any drift. The filter definitions in the workflow are the authority on exactly which paths set each flag.

### Jobs that always run

These jobs run on every PR, whatever it touches: `changes`, `lint`, `dependency-audit`, `zizmor`, and `actionlint`. The terminal jobs `coverage-upload` and `ci-gate` run too, unconditionally (`if: always()`). Which side a job belongs on is derived from its own gating, so the doc-closure gate ([below](#the-lint-and-freshness-gates)) recomputes this list and the table below against the workflow on every PR.

### PRs that touch no filtered path

A PR that sets none of the flags skips every job in the table above. A docs-only PR is the common case, unless it touches a file a suite holds: those carry a flag of their own (the contributor contract files and the `suiteHeld` set). The always-on jobs still gate such a PR, and two mechanisms keep it mergeable:

- `ci-gate` counts a skipped job as passing (below), so the aggregate
  verdict stays green.
- `coverage-upload` detects that no coverage artifact exists and issues a Codecov **empty upload**. That keeps Codecov's statuses from waiting forever: the required `codecov/patch` status is reported as passing.

### The lint and freshness gates

The `lint` job runs the checks below, in its own order, not the table's. The sync-shared freshness gate runs in `unit-tests`, and clippy runs in the Rust jobs. Each row names the local command (see [Running CI locally](local-ci.md) for running whole jobs).

The Doc closure row's own check holds this table to the properties it can recompute:

- `package.json`'s `lint` chain runs exactly the `lint:*` family.
- Every `lint:*` script and every `npm run` step of the `lint` job has a row here.
- Every `npm run` command a row cites names a real script (held by the check's citation leg, which reads all tracked markdown).
- Every job a Where cell names is a job the workflow defines.
- A row claiming an `npm run` gate resolves to a step one of those Where jobs actually runs.

A row whose local command is not an `npm run` form is held to its Where jobs only. Whether such a job still runs that gate stays held by review there, unless a gate of its own holds those jobs to carrying the step, as §CI-1's does for the Clippy row.

A row claiming an `npm run` gate is held further. The gate must open a command segment of one of those jobs' steps, either as the `npm run` invocation itself or as the script's own command. So a gate moved into a step form outside those two (a composite action, say) reds until the row or the step is re-shaped. That resolution does not decide _which_ step it found. Any step of a Where job running the command satisfies the claim. Step-level `if:` conditions are not read, so a step gated to pull requests still resolves one. A row whose local command is a reproduction or fix recipe rather than the gate's own invocation (as in the sync-shared freshness row, whose gate is the `git diff` that follows the sync) therefore resolves through the step that prepares the check rather than the one that fails it, and its liveness stays held by review.

Those resolutions read the Where cell and the local command. The Gate cell is read for the row's name, and no two rows carry the same name. A row another check selects by name, as §CI-1's Clippy row is, is held to that name by that check. What the name says is review's to judge: whether it describes the gate, and whether the step that runs the gate carries a `name:` saying the same.

### Dependency and license audit

The `dependency-audit` job runs on every PR and push. On the npm side, the advisory gate is [`check-npm-advisories.js`](../../scripts/check-npm-advisories.js) (`npm run check:npm-advisories`). It reads `npm audit` at level high in every npm root (the directories carrying a tracked `package-lock.json`, the roots the license gate below scans). It holds every high or critical advisory to the check's in-file ignore list, the counterpart of `deny.toml`'s advisory ignore list on the Rust side. Every entry carries an advisory id, a package, a reason, and an `until` day: the last day the entry holds, so the gate reds the day after. An entry names its root when that is not the repository root. The script's header states the verdicts and the upkeep rule: how an entry is added or renewed, and when a stale, expired, fix-available or wrong-package entry is deleted, refreshed or corrected. Then a default-deny license allowlist ([`check-licenses-npm.js`](../../scripts/check-licenses-npm.js), `npm run check:licenses`) is scanned over every real install root.

On the Rust side, `cargo deny check licenses` and `cargo deny check advisories` run as separate steps, so a red gate shows which failed. [`deny.toml`](../../packages/desktop/src-tauri/deny.toml) configures them. Both run a second time over the Win32 bindings generator's own lockfile ([`tools/bindgen`](../../packages/desktop/src-tauri/tools/bindgen/Cargo.toml), a crate of its own outside the application's dependency graph), under the same `deny.toml`. All of it blocks.

### Coverage and the Codecov statuses

The four coverage-instrumented jobs (`unit-tests`, `extension-e2e-tests`, `desktop-rust-tests`, and `desktop-integration-tests`) stage lcov artifacts, which the terminal `coverage-upload` job collects and uploads to Codecov. The other test jobs stage none. The reference server's, the reference control client's and the reference MCP server's suites are the three never coverage-measured. The corpus and vector jobs' test content is measured inside `desktop-rust-tests` and `unit-tests`.

The required status is `codecov/patch`, configured in [`.github/codecov.yml`](../../.github/codecov.yml) with a fixed target over the lines a diff changes. A diff with no coverable lines passes it as "coverage not affected". The empty upload ([above](#prs-that-touch-no-filtered-path)) keeps it from waiting on a commit no test job measured. The `codecov/project` status and the per-flag and per-component statuses that file configures are informational ([below](#required-vs-informational)). How coverage is measured, the flag taxonomy, and the staging and carryforward mechanics: [coverage reporting](../test/strategy/coverage.md).

### The aggregate gate (`ci-gate`)

`ci-gate` needs every other job in the workflow except `desktop-e2e-tests` (until its green week, above), always runs, and fails if any of them ended in a state other than success or skipped. It exists so the whole graph reports one aggregate verdict: the single check an external merge requirement can key on.

## Scheduled runs

### Weekly mutation run

[`mutation.yml`](../../.github/workflows/mutation.yml) (Mondays, plus manual dispatch) runs two tools:

- Stryker over the shared, extension, and desktop JavaScript packages. Each config ([`stryker.config.mjs`](../../stryker.config.mjs), [`stryker.extension.mjs`](../../stryker.extension.mjs), [`stryker.desktop.mjs`](../../stryker.desktop.mjs)) sets a `thresholds.break` floor that fails the run when the mutation score drops below it.
- `cargo-mutants` over the desktop crate modules that [`mutants.toml`](../../packages/desktop/src-tauri/.cargo/mutants.toml)'s `examine_globs` enumerates. The Rust job currently runs in measurement posture: missed-mutant and timeout exit codes are tolerated, and the counts are reported to the run summary while the baseline is established.

Mutation is a standing repo-health gate on this schedule, never a per-PR check. The strategy and scope decisions are in [mutation testing](../test/strategy/mutation.md).

### Weekly docs-disposition audit

[`docs-disposition-audit.yml`](../../.github/workflows/docs-disposition-audit.yml) (Tuesdays, plus manual dispatch) runs [`docs-disposition-audit.js`](../../scripts/docs-disposition-audit.js): a non-gating, aggregate-only audit of merged PRs' "unaffected" judgments. It measures the rate at which a later change edited a doc an earlier, area-overlapping PR judged unaffected. It is a review-calibration signal, never a per-PR verdict. Documentation-reorganization PRs are excluded as evidence, and the workflow header registers its own retirement criterion.

### Weekly pin-history probe

[`pin-history.yml`](../../.github/workflows/pin-history.yml) (Wednesdays, plus manual dispatch) runs [`check-pin-history.js`](../../scripts/check-pin-history.js) (`npm run check:pin-history`). For every SHA-pinned action, it asks GitHub's REST API for the upstream repository's default branch and compares that branch with the pin. The run is red when a pin sits off that branch's history, when the compare cannot find the pinned commit, or when the upstream repository is gone. A run that meets an answer the probe does not read, or no network, is red on the probe's own machinery verdict beside those. It is the hold on the policy [below](#pins-reference-stable-history).

The probe depends on an outside service (its availability and its limits), so it runs on this schedule, and a per-PR run is not part of it. A pin bump is probed at the next weekly run. A rate-limited run is the machinery verdict and reads as such. A red run blocks no PR.

### Scorecard

[`scorecard.yml`](../../.github/workflows/scorecard.yml) (Mondays, plus push to `main`, branch-protection changes, and manual dispatch) runs the OpenSSF Scorecard: a posture check over signals like action pinning, token permissions, dangerous workflow patterns, and branch protection. It is monitoring only: results upload as SARIF to the Security tab and never block a PR. Publishing results to the public scorecard site is off by design. Its publish verification rejects SHA-pinned actions as impostor commits, which conflicts with the pinning policy below.

## Job bounds and caches

### Every job carries a bound

Every job of every tracked workflow carries a `timeout-minutes` bound. It is a ceiling, not a budget: it caps how long the work under it can run, and it sits above what that work has been measured to take. Where a workflow header frames the numbers its own jobs carry, that header is their owner, and this guide cites it rather than restating them. [`test.yml`](../../.github/workflows/test.yml) and [`mutation.yml`](../../.github/workflows/mutation.yml) each open with theirs. Raising a bound is an edit to its own line, made against measurement.

The one shape that carries none is a job that calls a reusable workflow. The platform admits no `timeout-minutes` there, and actionlint refuses a file that writes the key on such a job. That is the `test` job each publish workflow gates on ([above](#the-workflow-inventory)). Its work is bounded by the job bounds of the workflow it calls.

Some steps carry a bound of their own: a step where a job's time actually goes, or one that can stop making progress without failing (a browser download, a registry install, a suite run). A job's step bounds add up to less than its job bound. A job bound its step bounds could reach may fire before the last bounded step's own bound does. That step would then end by the job's cancellation rather than by its own bound, and the steps after it would never run. Steps with no bound of their own stay outside that sum.

When a bound fires, the step or the job ends there and the run is red. A bound turns a hang into a failure at a stated number rather than at the platform's own limit. The Job bounds and caches gate ([above](#the-lint-and-freshness-gates)) recomputes both properties over every tracked workflow: the bound each job carries, and the step bounds adding up below it. It leaves each number itself to the workflow file that states it.

### What the caches key on

The Job bounds and caches gate ([above](#the-lint-and-freshness-gates)) recomputes the key-families and pinned-tools tables. It reads them from the workflow files, and the Doc mention column alone from the [`local-ci.md`](local-ci.md#the-mutation-runs) subsection named with that column below. A cell that stops describing the surface it names reds, and so does a cache step no row describes.

The **key families** table has one _row_ per writing job _name_, taken bare across the tracked workflows. A job writing two families would have no single row to take, and neither would two jobs that share a name and each write one. So a name may write a family cache once. The gate refuses either shape on its own exit code rather than describing it.

In the cache store, a family holds one entry per platform it spans and per lockfile generation (`xcompile` spans two platforms). The family segment together with the key suffix keeps one job from overwriting another's. A cache key is the Family cell followed by the Key suffix cell. Fallback is the step's `restore-keys`. A restore candidate, exact or by prefix, comes only from entries saved under the same Paths list, so a prefix reaches nothing stored under a different one. Save states the posture. _main ref + exact miss_ is a restore/save split whose save runs only on `main`, and only where the restore was not an exact hit. So a pull request reads `main`'s entry and writes none.

The families are grouped by their **exact** Paths list, so a group is the whole of what a family's keys can reach (see Fallback above). Two lists that merely overlap are still two stores. Inside each group the family names are held pairwise prefix-free. Two writers share one name only where their keys hash different inputs.

The fallbacks are held with them: the ordering for every family, and the reach inside that same group.

- **Ordering.** Where a family states any fallback, the first is its own prefix, whatever its group holds beside it. The list is tried in order, and each prefix serves the most recent entry matching it. So anything ahead of the family's own prefix either serves a sibling's newer entry before this family's, or reaches nothing at all.
- **Reach.** Inside one group, a family sharing its stem with another states no fallback at all. The hash is the whole of what tells those two entries apart, so any prefix on that stem drops it and serves the other writer's artifact. Where a family does not share its stem, a fallback reaching a _different_ stem in the group is the deliberate warm start the Fallback column records, and is left to that record.

The families listing the registry, the git checkouts and the desktop `target/` tree (`rust-tests`, `vectors` and `xcompile` in the table above) form one group. `vectors` reaches a sibling's registry through the bare `${{ runner.os }}-cargo-` fallback. `rust-tests` and `xcompile` name only their own prefix and stay inside it.

The `rust-tests` family also names the toolchain: its prefix carries the `cachekey` output of the job's `dtolnay/rust-toolchain` step, and so does its one fallback. Its job measures coverage over the tree it restores. `cargo llvm-cov` reports on every test binary under its target directory whose name matches a workspace target, while its clean (`cargo clean --package`) reaches only the files the current toolchain's layout names. A tree another toolchain built would keep that toolchain's test binaries. Their mappings, built from older source, would join the report as never-hit lines (#700). So a lockfile bump warm-starts from this family's own tree under the same toolchain, and a toolchain move starts cold. The bare `${{ runner.os }}-cargo-` prefix is not listed because it would match this family's own older keys as well. The gate holds that shape for any family whose job runs `cargo llvm-cov` over a cached `target` tree: the toolchain segment in the prefix, naming a `dtolnay/rust-toolchain` step of that job by its id, and in every fallback. The other families' trees are never walked that way. A leftover there costs space and not correctness, so they keep the shorter key.

The `mutation` family caches no `target/` directory. Its job mutates and builds in the real tree, and a tree carrying post-mutation fingerprints must never seed a later run. That shorter list makes it a group of one: nothing reaches its entries and it reaches nothing else's, which is why its fallback names only itself. Its job runs weekly against a seven-day inactivity eviction, so a missed week starts cold. That is accepted design, stated here and in the step's own note.

The two Playwright entries are a group of their own. They share one family prefix, and the lockfile each key hashes is what tells their entries apart. That is why neither states a fallback, and why neither may grow one.

The **pinned tools** are each cached as the single file its install leaves in `~/.cargo/bin`. The key's version segment names the version the same job's `cargo install` pins, so moving to a new version is a new key and a fresh install. Doc mention is the version [Running CI locally § The mutation runs](local-ci.md#the-mutation-runs) states beside that tool's own name, or `none` where it states none. That one subsection is the whole of the guide text this column is read from. Where a version is stated, it is held to the pin, so the segment, the pin and the guide move together or red.

This table states no Save column because every row has the same posture, and it is not the families' posture: _every run (post-job save)_. Each tool cache is one combined `actions/cache` step with no condition of its own and no ref gate. So any run of the job carrying it restores the entry, and where the key missed, the action creates one. As its documentation puts it, "a new cache is automatically created provided the job completes successfully". Nothing scopes that write to a ref, which is where this posture parts from the families'. Which runs reach it is then the job's own gating:

- `cargo-deny` sits in the always-on `dependency-audit` job;
- `cargo-llvm-cov` in the path-filtered `desktop-rust-tests` job;
- `cargo-mutants` in a workflow whose runs are its weekly schedule and its manual dispatches.

The key already carries the runner OS and the pinned version, so those writes cannot collide. A family cache, whose save is gated on `main`, is the one that would, and its split keeps it from doing so. The difference is a considered exception, taken on that ground.

The table keys instead on the tool, one row per tool name. A second job caching a listed tool has no row to take, and the gate refuses that shape on its own exit code: the mirror of the families' one-cache-per-job limit above. What the gate recomputes of all this is the table itself: its cells (the tool, its key's version segment, the install pin and the Doc mention) and that one-row-per-tool limit. The posture, the step shape and the job placements stated here for the tool caches are read from the workflow files by hand. So a tool cache later written as a gated split, or moved to another job, would leave them stale with nothing red.

## Action pinning and workflow security

### Every action is pinned to a commit SHA

Every third-party action or reusable workflow referenced by a `uses:` line is pinned to a full 40-character commit SHA. A trailing `# version` comment names the release, tag or branch the SHA was taken from. The enforcement is [`check-action-pins.js`](../../scripts/check-action-pins.js), run in the `lint` job on every PR (`npm run check:action-pins`). It scans every workflow file and every composite action under `.github/actions/`, and fails on any ref that is not a commit SHA. Local refs (`./…`: this repository's own composite actions and reusable workflows) are exempt, since they live in this tree and are reviewed as part of it.

The offenders and the count of what was read come from one pass over those files. The green line states both (how many `uses:` references were found, and across how many files), so a pass says what it looked at. Two shapes where that read finds nothing are refused on the check's own exit code rather than reported as a clean tree: a scan of the two roots that yields no file, and a file set stating no `uses:` reference between them. A single file without one is ordinary and is not refused.

A mutable tag (`actions/checkout@v7`) can be re-pointed at different code by whoever controls the upstream repository; a commit SHA cannot. Dependabot's `github-actions` ecosystem entry ([`dependabot.yml`](../../.github/dependabot.yml)) bumps the SHA and the trailing comment together on its weekly run. A same-action pin bump is one of the diffs the docs-disposition check recognizes as dependency-only. The comment is a human/Dependabot-readable alias, not a contract: only the SHA is verified. That is also why zizmor's ref-version-mismatch audit is disabled (see [`zizmor.yml`](../../.github/zizmor.yml)).

### Pins reference stable history

A SHA pin is only as durable as the history it lives on. A commit taken from a branch the upstream force-pushes stops being fetchable when that history is rewritten, and every job using it fails. The policy is therefore to pin commits reachable from the upstream's default branch (the history an upstream does not rewrite), and to select versions through action inputs where the upstream supports it. The toolchain action is the live example. `dtolnay/rust-toolchain` is pinned to a commit on the upstream `master` history, and the toolchain is selected with `with: toolchain: stable`, never by pinning a SHA from the action's per-release branches, which are re-pointed on each Rust release. The [weekly pin-history probe](#weekly-pin-history-probe) holds every pin to its upstream's default-branch history.

### Workflow permissions and credentials

The posture, as the workflow files state it:

- Every workflow declares a top-level read-only `GITHUB_TOKEN`: `permissions: contents: read`, plus `pull-requests: read` on the docs-disposition audit (it reads merged PRs), and `read-all` for Scorecard. Jobs that must write elevate only themselves, scope by scope: the CLA job (`actions`/`contents`/`pull-requests` write), the Scorecard SARIF upload (`security-events` write), and the publish jobs (`contents`/`pull-requests` write).
- Every checkout sets `persist-credentials: false`, so later steps never
  inherit the checkout token.
- The reusable test suite declares exactly one secret (`CODECOV_TOKEN`). The publish workflows pass it explicitly instead of `secrets: inherit`, so the suite never receives the full repository secret set.
- Values from PR-controlled event fields (the PR title, the PR body) reach
  the check scripts via environment variables, never shell interpolation.
- The one dangerous-trigger exception is `cla.yml`'s `pull_request_target`, required for fork PRs. The SHA-pinned action and the job's `if:` allowlist mitigate it, and [`zizmor.yml`](../../.github/zizmor.yml) documents it as an accepted finding.

### The workflow auditors: zizmor and actionlint

Two blocking jobs in `test.yml` audit the workflow files themselves on
every PR:

- **zizmor**: static analysis for template injection, dangerous triggers, cache poisoning, and token scope. Both the action and the tool version are pinned, so a zizmor release cannot surprise-break CI. Accepted findings live in [`zizmor.yml`](../../.github/zizmor.yml), each with its reason (the ref-version-mismatch style audit, the cache-poisoning false positive on the publish workflows, and the `cla.yml` trigger above). Anything new fails the gate.
- **actionlint**: workflow syntax, expression typing, and shellcheck over `run:` scripts. It runs via a digest-pinned Docker image, so CI matches the local `docker run rhysd/actionlint` check. Intentional shellcheck exceptions are annotated inline with `# shellcheck disable=…`.

[`lefthook.yml`](../../lefthook.yml) installs two Git hooks:

| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| ESLint                                                                                           | Every push                                                                                                                                             | It covers fewer trees than CI's `lint:js`, as stated below the table |

The hook's ESLint call enumerates the package source trees, the extension

The hooks are installed by `lefthook install`. The `lefthook` package's own install script runs it on an install that places the package (a fresh clone's `npm install`, any `npm ci`). That script skips when the `CI` environment variable is set to anything but empty, `0` or `false`, unless `LEFTHOOK` is set the same way, so CI runners carry no hooks. npm's install-script policy must allow the script, which the default does with a notice.

## Required vs informational

The repository's rules for `main` decide whether a red check blocks a merge. They are a ruleset, since the branch carries no classic branch protection, and they are repository settings, not a tracked file. What the repository itself shows:

- `ci-gate` aggregates the whole test suite into one always-reported result, built precisely so a single required check can represent the job graph.
- The workflow and [`.github/codecov.yml`](../../.github/codecov.yml) comments name `codecov/patch` as the required Codecov check, and the `codecov/project` status that file configures as not required. The empty-upload path exists so the required check is reported even on PRs that produce no coverage.
- [PUBLISHING](../../.github/PUBLISHING.md#test-gating-and-the-version-pr)
  records that `main` requires zero approvals: the automated version-table
  PR merges on green checks alone, with the release-output guard as the
  real gate.
- As repository-settings behavior (visible only in the settings UI, noted here for completeness), the repository's ruleset for `main` requires:
  - the status checks `ci-gate`, `CodeQL`, `codecov/patch`, `cla_assistant`, `conventional-title` and `disposition-format`;
  - the branch to be up to date with `main`.

Informational today (these do not block):

- the schema-version impact step in `unit-tests` (`continue-on-error`);
- the `codecov/project` status (which `.github/codecov.yml` configures beside `codecov/patch` and no ruleset requires);
- the per-flag and per-component Codecov statuses (declared informational in `.github/codecov.yml`, which marks the per-flag declaration as advisory-for-now);
- the Codecov PR comment;
- Scorecard;
- the weekly docs-disposition audit;
- the weekly pin-history probe;
- the `cargo-mutants` job's current measurement posture;
- the next-release-version suggestion;
- the numbers the words before and after report shows in `lint` (its row in [the lint table](#the-lint-and-freshness-gates) holds the one way it reds).
