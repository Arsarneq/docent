# End-to-End Tests — Desktop

The desktop app's end-to-end suite: the built app on Windows, driven through its own panel, with real keyboard and mouse input for other programs, dialogs and, where a test is about it, the app's own window, checked by the file it exports. It is the end-to-end layer of [the test pyramid](../strategy/test-pyramid.md) for the desktop. The [integration suite](../integration/desktop.md) drives the panel against a mocked backend, and the [Rust tests](../desktop-rust.md) send real input to windows they create and read the capture layer. This suite runs the built app as a whole. It checks the route it drives the app by, and records real input from the hooks through the panel's commit to the exported file (below).

The suite lives in `packages/desktop/tests/e2e/`. It runs in the `desktop-e2e-tests` job of [CI](../../guides/ci.md#path-filtered-test-jobs), on the pinned `windows-2022` image.

## The route

Each test drives the app with two hands:

- **The panel**, as a page. The fixture (`helpers/desktop.js`) starts the release build with WebView2's DevTools port open (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=…`) and connects Playwright to it. A test clicks the panel's own buttons, so each click runs the panel's handler and the real backend command behind it. The clicks go through that protocol, not as operating-system input, so a click on the panel does not move the foreground the way a person's click does.
- **Other programs and dialogs**, with real keyboard and mouse input, and the app's own window where a test is about a key or click a person gives it. The [input driver](../../../packages/desktop/tests/e2e/driver/README.md) sends `SendInput` keys and clicks from a steps file and checks, before each step's input, that it goes to the window the steps named. `helpers/front.ps1` brings a program's window, or its open dialog, to the front first. When the window is not already in front, it presses an unassigned key to be allowed to (not Alt, which would put a window with a menu bar in menu mode and lose the next key), so it is called before a recording starts.

Each test starts the app on a data folder of its own: the fixture points `APPDATA`, where the app keeps its projects, at a new temporary folder, and ends the app and its WebView processes afterwards. When a test fails, the `app` and `notepad` fixtures print every visible window (process, class, title) to the job log and attach a screenshot (`helpers/screen.ps1`) before they end the app or Notepad.

## Retries and flaky tests

One worker: the tests share the machine's keyboard, mouse and foreground window. A failed test runs once more, traced, so the run keeps a trace of it. A test that passes only on that retry fails the run (`failOnFlakyTests`). When a test fails, the job uploads `test-results/` (artifact `desktop-e2e-results`) with its trace and screenshot; a green run writes nothing there, so it uploads nothing.

The job runs the driver's own tests first, before it builds the app: the planner's (`driver/plan.test.mjs`) and the window test (`driver/drive.test.ps1`). A red window test means the keys or clicks do not arrive on that runner, and the job stops there, in minutes instead of after the build.

## Running the suite

On a Windows machine nobody is using, since the suite takes over the keyboard and the mouse, as a Windows user with no Docent API keys stored and any installed Docent closed. The suite's app keeps its projects in a temporary folder, but it shares the WebView folder and Windows Credential Manager, where the app keeps its keys, with an installed Docent of the same user:

```powershell
npm ci
npm run sync-shared
npm run build:desktop-dist
cd packages/desktop/src-tauri
cargo build --release --features tauri/custom-protocol
cd ../tests/e2e
npm ci
cd ../../../..
npm run test:e2e:desktop
```

`DOCENT_DESKTOP_EXE` points the fixture at another build of the app.

`DOCENT_CAPTURE_TIMINGS=1` in the app's environment turns on the capture timings. Each time a capture stops, the app writes one block to stderr: for each step of the typing worker, the largest and second largest duration in ms, and for the looks at the focused control ahead of any key, how many described it and how many were skipped, by reason. An app ended while it records writes none. A key written masked, a press of Shift, Ctrl or Alt, and a value change whose value is not written are not measured. A release build has no console, so the block is seen only where the launcher redirects the app's stderr. The block holds fixed words and numbers only, the words of [`timing_lines.rs`](../../../packages/desktop/src-tauri/src/capture/timing_lines.rs), and no count or order of what was typed; the switch is off by default and changes no action. The worker-pool tests `with_the_timing_switch_on_one_block_is_written_when_the_capture_stops`, `the_timing_block_has_one_shape_whatever_was_typed_into_a_password_field`, `a_timing_block_holds_only_fixed_words_numbers_and_the_placeholder`, `with_the_timing_switch_off_nothing_is_written_and_the_actions_are_the_same` and `a_look_ahead_at_a_gone_control_counts_under_gone` hold this; `npm run test:desktop:rust` runs them.
